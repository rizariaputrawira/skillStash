# Model Manager Fraud Ops KPI reference

Load when implementing or reviewing a Model Manager custom KPI for fraud-model monitoring. [Fraud review](fraud-review.md) owns mature-label, denominator, owner and threshold rules; use its monitoring plan rather than duplicating the approval workflow. This original reference is not an adaptation of the CC BY lifecycle template. Source pins and license boundaries are in [SOURCES.md](../SOURCES.md).

1. **Bind prerequisites.** Identify Model Manager project/model revisions, CAS session/server/caslibs, actual performance-table/window layout, ground-truth source and label maturity, score-code and ASTORE identities, and availability of `%MM_KPI_ACTIONSET` and `mmkpi.addCustomKPI`. No minimum target release follows from the sample or documentation edition. Without CAS/registration authority, finish the offline calculation and implementation plan only.
2. **Separate sample mechanics from policy.** The sample uses four hard-coded quarterly tables and transforms probability with `500 + (10 / ln(2)) * ln(p / (1-p))`. Its buckets are `< 320`, then lower-inclusive/upper-exclusive intervals of width 20 from `320 - <340` through `560 - <580`, then `>= 580`. Outputs include `Bucket`, `Fraud_Count`, `Total_Count`, `Genuine_Count`, `TimeSK` and `TimeLabel`. These illustrate aggregation, not production thresholds or fraud-loss estimates. A configured model ID is not proof that scoring selected the intended revision; verify score-code/ASTORE linkage independently.
3. **Validate population before aggregation.** Require known event-class mapping and mature labels. The sample's `(FRAUD_LABEL=1)` expression can collapse unresolved labels into non-fraud; preserve unresolved counts separately, never as genuine. For missing/nonfinite p, `p <= 0` or `p >= 1`, flag invalid transform pending owner-approved policy before evaluating the logarithm. Do not invent clipping, place missing scores in an ordinary bucket or silently modify the model. Aggregate only mature valid rows with explicit exclusions and denominators; empty windows have no measurable outcome, not fabricated zero/passing performance. Preserve period identity and reconcile input, included, unresolved and invalid counts without double-counting overlapping exclusions.
4. **Plan authorized table effects.** Define isolated owned output/temp tables and reviewed lifetimes before execution. The sample loads and scores data, creates/drops tables, promotes a table and changes project KPI data. All such effects, including subsequent `mmkpi.addCustomKPI`, require authorization. Do not copy shared hard-coded table names, Public caslib assumptions or blanket cleanup. Review session scope and table ownership before any scoped cleanup.
5. **Verify registration separately.** Aggregation output is prepared data, not successful KPI registration or an active monitoring schedule. Review tracking columns against the exact target contract: official guidance recommends `TimeSK`, `TimeLabel` where applicable, `ProjectUUID`, `Datetime`; model-specific last-run use needs `ModelUUID` and `ModelName`. `%MM_KPI_ACTIONSET` defines the action set; `mmkpi.addCustomKPI` adds data/columns to the project's standard KPI table. After separately authorized registration, inspect CAS action status/severity and freshly read the intended project/time/model result. Duplicate/rerun semantics depend on the target contract: reconcile before resubmission rather than appending blindly. Scheduling and operational ownership need their own evidence.

## Return

Return prerequisite/revision evidence; window/class/maturity and transform policy; bucket totals with fraud/genuine counts; separate unresolved-label and invalid-transform counts; denominator reconciliation; proposed table lifetimes/effects; registration/read-back plan or actual evidence; and outstanding owner decisions. Label supplied/offline calculations explicitly. Do not claim CAS execution, KPI registration or active monitoring when only a plan was prepared.
