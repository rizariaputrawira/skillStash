# Configure classifications, scope, schemas and profiles

Load when creating or changing the assets that rules will consume: classification hierarchy, organization/project access, message schemas, variable sets, entity keys or profile variables. This is a practical configuration recipe, not an executed change. Apply its UI operations only in the authorized target environment.

When choosing field types, Core request/result paths, serialization, component disclosure or schema/profile compatibility limits, read [message-schema reference](message-schema-reference.md). The creation workflow here does not by itself account for every field/property in the source manual.

## 1. Prepare the change and the right authority

**Inputs:** target release/namespace, authorized organization owner, existing asset identifiers/revisions, intended event classes, field contract, project users/roles and proposed entity key. Open **Detect Behavior** from the applications menu using the site-provided SAS Detection Definition URL. Do not substitute a sample hostname.

1. Separate three permission systems before changing membership (A pp. 17–24, 33; M pp. 1–2, 48):
   - **Detection roles/capabilities:** roles are custom groups that belong to **SAS Detection Roles**. Assign users to a member role, not directly to that root group. Organization-scoped capabilities require the role to be associated with the organization and assigned to the user. Project-scoped capabilities additionally require project membership. View capabilities remain prerequisites for actions at that scope.
   - **Message schemas:** **SAS Detection Message Schema Editor** permits editing schemas the user can access; it does not itself make every restricted schema readable. **Message Schema Selected Access** determines which identities can be selected for restricted access. SAS Environment Manager owns role/group membership. SAS Administrators can access/edit all message schemas.
   - **Organization profiles:** organization **Membership Roles → Profile Editing** governs profile editing separately. A role without this permission has read-only profile access. The **SAS Detection System Administrators** role and its profile-editing permission cannot be removed from the organization.
2. Check the required operation capabilities, not just a familiar default role: `sda.message.classifications.manage` for hierarchy administration; `sda.organizations.create` / `sda.organizations.update` for organization creation/change; `sda.projects.create` / `sda.projects.update` for project creation/change, with the corresponding view scope. A missing navigation entry can be a missing `sda.navigation.*` capability, not missing data.
3. **Original safeguard:** record the requested operation, approver, target identifiers and intended access. For contract/state/routing acceptance design, load [strategy-assets.md](strategy-assets.md); it owns that review rather than this configuration recipe.

**Finish:** a named authorized actor can reach the relevant view and has the action, view and membership prerequisites. If not, return the exact missing capability/group/scope to the identity or organization administrator; do not broaden access as a workaround.

## 2. Build or extend the classification hierarchy

**Inputs:** approved parent node, proposed internal/display names and, for imports, namespace-wide or selected-parent CSV semantics. **Output:** saved hierarchy nodes and their actual key codes. Source: A pp. 25–32.

1. Open **Message Classifications**. There is one hierarchy per namespace, with a single **Global** root, at most eight levels and up to 9,999 children per node. Select the intended parent; **Filter** highlights matching names.
2. For one child, right-click its parent and choose **Add**. In **New Message Classification**, enter **Display Name** (up to 75 characters) and **Name** (up to 16 letters, numbers, hyphens or underscores); **Save**. Record the saved child and parent rather than inventing its assigned code.
3. For a hierarchy import, use the import action that opens **Import**, then **Browse → Open → Import**. The CSV header uses required `keyCode,name,displayName` and optional `createdBy`. Whole-hierarchy key codes express the full dotted path, extending the parent's key; each segment is 1–9999. Internal names are unique, at most 16 permitted characters; display names are at most 75 characters; `createdBy` is at most 40 characters.
4. For a subtree import, select the parent and right-click **Import**. Its CSV codes are **relative to that selected parent**: under an existing parent `1.7`, imported keys `1` and `2` become `1.7.1` and `1.7.2`. Do not reuse full-hierarchy path semantics for this operation. Inspect the parent selection before importing.
5. For a display-name correction, right-click **Edit**, change **Display Name**, then **OK**. A matching CSV `keyCode` can also replace an existing display name during import; review the import as an update, not necessarily append-only. Right-click **Delete** requires confirmation; use it only for the approved deletion scope, not for repairing an import blindly.

**Verify/finish:** require the success message and inspect actual nodes, parent paths and display names; retain imported file identity and resulting mappings. On an import error, use its reported invalid data to correct the file and review already-visible nodes before retrying. The cited procedure does not establish import atomicity or automatic rollback.

## 3. Create reusable message contracts before associating them

**Inputs:** approved name, access audience, field definitions and reusable components. **Output:** a Developing schema with a verified variable tree and access scope. Sources: M pp. 1–4, 19, 27–35, 37–45.

1. In **Message Schemas**, choose **New message schema**. Fill **Properties**: a unique name using letters, numbers, underscores or spaces; optional description/tags; and a type using lowercase alphanumeric characters. The name cannot be changed after creation and the type cannot be `profile`. The root variable set is created automatically.
2. In **Access**, select **All users** or **Selected users and groups**. The latter requires at least one selectable identity; the creator is initially selected. Save/finish the wizard and inspect the created form. Decide the audience **before** organization/project association: once in use, access can expand but cannot become more restrictive. **All users** is therefore not a reversible convenience for an in-use schema.
3. Select the root or intended local parent variable set and use its create-variable-set control to open **New Variable Set**. Enter a unique case-insensitive name of up to 127 letters/numbers/underscores, optional description, and **Object** or **Array of objects**. For arrays set the maximum explicitly; documented range is 1–1,000 and default is 10. **Save** and check the new set is under the intended parent. Nested sets are supported for message schemas; path-length limits are 4,000 characters for Postgres or 4,000 bytes for Oracle.
4. Select a set and use the right-panel create-variable control to open **New Variable**. Enter unique **Name** (up to 127 letters/numbers/underscores) and **Display Name** (up to 255 characters), then choose access and **Data type**. **Read Only** is the default; **Read Write** permits rule mutation, and this access type cannot be changed after saving. Available types include Big integer, Boolean, Currency, Date, Integer, Number, String, Time and Timestamp.
5. Set string length, optional array **maximum items**, non-array default, and any approved **More → Limit values** values/range. Array variables allow 1–1,000 items, default 10; they cannot have a default value. Use **Required** only when absence should cause message rejection. Use **Deprecated** to signal planned retirement; it does not itself remove a field. Save and inspect **Type**, **Length**, **Access**, **Default Value** and the **Rules** reference count.
6. For approved string masking metadata use **More → Data masking**. M explicitly makes presentation dependent on the consuming tool; this setting is not proof that every output or log is masked.
7. To reuse another schema, open the composite schema, select the variable set where the component belongs, and use the linking control to open **Choose Message Schemas**; select the accessible components and **OK**. An incoming **ION** message's schema must include **Core**. Core is supplied read-only; do not recreate or edit its standard variables. Profile schemas cannot be components.
8. Check link visibility before saving: an **All users** schema can link only to other all-user schemas. A restricted composite can link to public or restricted components; its readers can see component content through the composite even without independent component access. Linked content is read-only in the composite; edit the component itself. A component change affects the composites that link to it.

**Verify/finish:** reopen the schema, verify full field paths/types/lengths/access/array bounds and component placement against the input contract, and confirm the intended reader can see the composite. Resolve name/path/property conflicts before association. If a key field was mistakenly numeric, or variable access was saved incorrectly, assess dependent assets before replacing it; do not silently coerce identifiers or claim an in-place access-type change.

## 4. Create the organization, then its projects

**Inputs:** saved classifications/schemas, roles with actual users, intended project subset and optional existing lists. **Outputs:** organization, generated profile schema, projects and membership/association records. Source: A pp. 67–75, 119–125.

1. In **Organizations**, choose **New organization**. Enter **Display Name** (75 characters maximum), **Name** (16 maximum; letters/numbers/hyphens/underscores/spaces) and optional description. Confirm the derived internal name explicitly rather than trusting display-name truncation.
2. Follow **Next** to assign classifications, membership roles, **Profile Editing** permissions and at least one message schema; optionally assign advanced lists; **Finish**. Keep the automatically added **SAS Detection System Administrators** role. Add a role you belong to with organization-modification capability if you must continue managing the new organization. Review the default-enabled profile-editing permission for each added role.
3. A schema cannot be associated if its variables have the same path/name as existing organization variables but incompatible properties, such as different type or length. Correct the conflicting contracts rather than renaming a field just to bypass this gate.
4. Open the created organization and inspect **Membership Roles**, **Message Schema**, **Profile**, **Projects** and **Properties**. Organization updates expose the association tab as **Message Schemas** in the cited procedure; use the matching installed tab rather than assuming this label variation is a distinct object. To maintain scope, add/remove roles and schema associations in their tabs and save the organization; role user membership changes belong in SAS Environment Manager. The classification tree in an opened organization is read-only in this guide.
5. In **Projects**, select that base organization and choose **New project**. An organization with no schemas or users cannot support project creation. Enter a name unique within that organization (up to 256 characters) and optional description; assign users; select at least one schema; select at least one classification; optionally assign advanced lists; **Finish**. Choices come from the base organization, not an unrelated organization. Each project belongs to only one base organization.
6. Inspect the project's **Message Schema**, **Message Classification**, **Profile**, **Membership** and **Properties** tabs. Selecting a parent classification selects its children; selecting a child also selects its parent. Review the resulting selections, not just the node clicked. `sda.projects.update` controls classification changes and whether the project's Profile tab is editable.
7. To maintain project users, open **Membership**, use its management control to open **Manage Users**, move the intended **Available users** to **Selected users**, and **OK**. To remove a user, select that user in **Membership** and use the remove control. Project membership alone does not supply role capabilities.

**Verify/finish:** require creation success messages and reopen both objects. Record actual organization/project identifiers, selected schemas/revisions, classifications, roles, users and profile-editing permissions. Confirm an intended member's scoped access and an out-of-scope actor's expected lack of access without changing privileges for the check. Organizations separate information despite sharing resources; schema catalogue availability is not proof of unrestricted schema access or project membership.

## 5. Define entity-keyed profile state

**Inputs:** organization-associated message-schema string fields, owning project and approved retention/sharing/state specification. **Output:** profile set with explicit keys and project-owned variables. Source: M pp. 47–61; A pp. 68–70, 120–121.

1. Use the organization's automatically generated profile schema, named after the organization; do not create another ordinary schema with type `profile`. Open it in **Profiles**, or open the organization's **Profile** tab. There is one profile schema per organization; profile schemas cannot link to one another and profile variable sets cannot be nested.
2. With organization **Profile Editing** permission, select the profile root and open **New Variable Set** with the create-set control. Enter the unique set name and select the approved key variables: up to ten **string** variables from schemas associated with the same organization. Specify **Cache expiration** in days, then **Save**. The documented default is 730 days; the signature is deleted after that many days without an update. This is an inactivity expiry, not evidence of a rolling aggregation window.
3. Select the set and the intended **Project**, then open **New Variable** with the right-panel create-variable control. Enter **Name**, **Display Name**, optional description and **Parent Project**. If the project was preselected, the parent is populated read-only. Choose **The parent project only** (default) or **All projects in this organization**, then type, applicable string lengths, optional array size, masking metadata and value restrictions. **Save** and confirm it is listed under the intended set/project.
4. Sharing grants other projects **read-only** rule access. Only the owning project can write the profile variable; an unshared variable is unavailable to other projects' rules. Creating a variable does not implement its initialization or update rule. If creating a variable from an existing rule instead, the documented **New Profile Variable** route also permits a non-array default (M pp. 55–59); do not assume the separate Profiles creation form has the same default field or that absent state equals zero.
5. Inspect **Type**, **Length**, **Rules**, **Access**, **Project** and **Sharing** in the profile table. The **Project** filter still shows shared variables from other projects. For a rule-integration check, the rule editor suggests accessible variables as `profile` is entered; presence in a suggestion list is not proof of correct state-update behavior.

**Verify/finish:** record the actual key field paths, set, cache expiration, owning project, variable definitions and sharing. Use the state-transition acceptance cases owned by [strategy-assets.md](strategy-assets.md) before rule deployment. If the desired key is absent from the picker, resolve its schema association and string type; do not substitute a different entity identifier. If the variable is read-only, check owning-project membership and profile-editing permission rather than duplicating the variable elsewhere.

## 6. Manage changes without confusing copy, version and deployment

Sources: M pp. 30–35, 38, 59–61; A pp. 72–75, 123.

- **Schema revisions:** open **Versions** and record the version marked **(viewing)**. Only the latest version can be **Developing**, and only Developing versions are editable; **Deployed** versions are immutable. **New version** creates a revision from the latest revision. Major/minor/patch have documented breaking-change/additive/attribute-change meanings, but record actual product-generated versions instead of predicting a version increment from that summary.
- **Promotion side effect:** for an organization-linked schema, the Detection Definition service checks for changes when a rule moves **Coding → Testing** and can create a new schema version and update the deployment; organization/deployment use the newest version. Capture schema revisions at handoff and after promotion. Do not treat a saved schema as a frozen deployment snapshot.
- **Copy:** for a non-profile schema, use the copy action to open **Copy Message Schema**, supply a unique name, and decide each reusable component's **Copy**, **Link**, or unchecked **Include** behavior. **Link** retains shared dependencies; **Copy** creates a separately named reusable schema. Review the resulting dependency tree; a copy is not an export, runtime deployment or automatic isolation of every component.
- **In-use limits:** breaking changes to an in-use Developing schema are restricted, including deleting a variable used by a rule. Deployed message strings and arrays cannot have their maxima reduced. Ordinary schema access cannot narrow once the schema is used by an organization/project; a restricted composite containing a restricted component cannot simply become all-user.
- **Profile edits:** use **Profiles → owning schema → set → Project → variable → Open** to reach **Variable Properties**, then **Save**. Editing/deleting requires owning-project membership and profile-editing permission. Deployed profile-schema variables cannot be edited. String data length and array size can increase, not decrease. Shared-to-private cannot be selected while rules in **Testing** or **Production** use the variable. In-use profile variables cannot be deleted; sets require their variables to be removed first.
- **Removal order:** review referencing rules first. Project schema/list associations cannot be removed while used by rules in **Testing** or **Production**. A normal schema can be deleted only as a Developing version with no message or organization relationships. Private/root variable sets cannot be deleted. Organizations with associated projects or rules cannot be deleted; do not delete those dependants merely to clear an unexpected error.
- **Deployment-related administration:** inspect organization **Advanced Settings** before handoff. **Automatically deploy changes** defaults to false; enabling it causes rule production promotions to initiate deployment after **Auto deployment delay**. **Automatically restart detection services** can restart after successful deployment. Record, rather than casually change, **Publishing destination**, **Deployment history expiration** (default 14 days) and **Schema generation** (**Necessary schema only** by default). The latter can omit schema portions unused by rules/models. **Detection URL → Test** checks that configured target; absence of the URL disables certain runtime controls. The guide requires consulting SAS before changing **Maximum message length** or **Deploy testing rules**; **Message dataset password credential** requires a SAS Administrator. These are administrator-owned settings, not necessary edits for creating a field.
- **Export boundary:** these cited asset procedures document CSV classification **import**, schema **Copy**, versioning and deployment settings, not a general asset export/restore workflow. Do not invent an **Export** action or treat an exported rule/package as a recoverable organization/profile backup. If asset export is requested, establish the release-specific supported export interface and coverage before offering executable steps.

**Recovery:** on a save/version/association refusal, retain the message and current object/revision, identify the exact access or dependency gate above, and revise only the authorized change. Neither a new revision nor a copied schema proves runtime rollback or migration of persisted profile signatures. Resolve an approved recovery/migration plan before destructive replacement.

## Synthetic consuming exercise and result

**Original exercise, not an executed test:** prepare `LAB_ORG`, classification child `LAB_CARD`, composite `LabMessage` with Core and an object set `event`, string `event.accountKey`, and integer `event.amountMinor`. Use a restricted training role chosen from actual selectable identities. Create project `LabReview` with that schema/classification. In the generated organization profile, create `AccountState`, key it to `event.accountKey`, explicitly set approved cache expiry, and create integer `eventCount` owned by `LabReview`, private by default. Never insert real account identifiers.

Consume this reference in dependency order: classification + message schema/components → organization/roles/schema association → project/users/subset → profile set/keys → profile variables → rule handoff. Expected preparation artifacts are the exact key path and string type, selected classification paths, resulting access memberships and profile owner/sharing; no count increment or decision is expected until an update rule is implemented. For a sharing exercise, a second project may read a deliberately shared variable but does not gain write authority. For a conflict exercise, propose a second schema with the same `event.accountKey` path and incompatible type: identify the organization association gate before attempting the change.

Return an asset-change record with: target release/namespace; requested versus completed operations; saved identifiers and schema versions/states; component links/copy decisions; organization/project associations and permissions; entity keys/expiry/variable owner/sharing; observed confirmation or error messages; configuration-only versus runtime verification status; blocked operations and their exact prerequisites. Mark every unperformed verification **not run**. Configuration completion means the assets are saved and their definitions/relationships are verified, not that a rule is deployed, profile values are correct, or a live message has been processed.
