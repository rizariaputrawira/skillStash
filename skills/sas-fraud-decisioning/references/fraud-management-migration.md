# Migrate Fraud Management content to SFD

## Applicability and authority

Load only for an explicitly requested **SAS Fraud Management → SAS Fraud Decisioning** migration. Source: supplied *SAS Fraud Decisioning: User’s Guide*, **2026.03**, March 17, 2026, `v_028-P1:frdpayug`, printed pp.201–208; [SOURCES.md](../SOURCES.md). This is not generic Viya content promotion and not a direct DS1-to-DS2 compatibility guarantee. Source extraction, uploads, manifest application and target deployment are distinct authorized effects.

The manual illustrates migration using an internal/mock HTTP hostname and contains awkwardly extracted commands and large encoded payloads. None is reproduced here as a runnable example. Resolve the actual approved HTTPS service base, request schema/media type and authentication through target documentation; never call the example host or send credentials to an inferred endpoint.

## Ordered procedure

1. **Inventory and freeze the scope.** Record source SFM version, organizations/business units, rule states and dependencies; target SFD release/namespace; approved read/write scope; protected export storage; and owners for reconciliation and cutover. Preserve source identities and hashes so conversion findings can be traced to the exact extraction.
2. **Obtain the delivered extraction programs.** The guide locates `sfm_configuration_extract.sas` and `sfm_rule_extract.sas` in SAS Environment Manager under **SAS Content → Products → SAS Fraud Decisioning → Migration**. Use the target-delivered versions; do not reconstruct them from this skill. Transfer only into an approved directory accessible to the source SOR batch (`bch`) account.
3. **Check extraction permissions and selectors.** Verify `SAS_SOR_BATCH` has the guide's required table-read privileges using the source administrator's release-matched list, not a broad database grant. Review the rule extraction's business-unit and state selectors before execution. The guide's rule extract defaults to the Default business unit and Production state; removing a business-unit selector can widen extraction, and an omitted state still defaults to Production. Do not assume an empty selector means all states. Run only the approved delivered programs with the source installation's supported SAS invocation.
4. **Verify and package the exports.** The documented programs produce `sfm_configuration_extract.json` and/or `sfm_rule_extract.json` under the source implementation's `etl/data` location. Inspect actual outputs, counts, parseability and selected business-unit/state coverage without logging sensitive content. Package the requested JSON exports in a ZIP; multiple approved rule extractions may be included. Do not add unrelated files or credentials.
5. **Convert to a target manifest.** For an authorized conversion request, the guide identifies the `rfcSolutionConfig` service's `/migration` operation, taking the export ZIP and returning a YAML manifest. Confirm exact path, content type and schema against the installed service before submission. Retain the returned manifest and extraction provenance separately; conversion is not target application.
6. **Resolve conversion issues.** Inspect the manifest's `issues` section and reconcile every warning/error, type mapping and dependency. The manual states core-variable mappings cannot be changed. If conversion requires a correction, fix the authorized source/configuration input and regenerate or use the documented correction process; do not silently reinterpret field types or edit a core mapping to suppress validation. Review converted rule semantics, entity keys, classification/schema scope, alert mappings and profile state using synthetic cases.
7. **Apply only the reviewed manifest.** Under explicit target-write authority, submit the validated manifest to the documented `/manifest` operation with the installed service's exact request representation. Preserve the returned request ID and status URL. Accepted submission is not successful application. Monitor the returned job status, retain errors, and inspect current target objects before any retry of a partial or uncertain write.
8. **Reconcile and prove behavior.** Compare target identities/counts/associations against the approved manifest and source inventory. Test converted rules and state behavior through [rules and runtime](rules-testing-deployment.md). Rule presence does not prove active deployment. Record source-to-target mapping, conversion exceptions, test results, actual deployment and approved cutover decision separately. Keep the source unchanged unless its retirement was explicitly authorized.

## Finish condition

Return source/version/selection evidence; delivered-program and export identities; conversion request/manifest and resolved issues; target application job/result; object reconciliation; semantic test evidence; deployment/cutover status; and unresolved owners/actions. Without live authority, finish the inventory, conversion/application plan and synthetic acceptance packet and mark extraction/upload/application unperformed. Do not fabricate an export, completed job or successful migration.
