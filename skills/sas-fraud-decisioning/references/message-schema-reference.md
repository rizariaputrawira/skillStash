# Message-schema types, Core fields and change checks

Load when defining field-level contracts, integrating a Core request/response, diagnosing schema discovery, choosing component reuse, or reviewing a schema/profile change. [Configure assets](configure-assets.md) owns the ordered creation/association/profile workflow; this reference owns its detailed field and compatibility checks. It grants no permission to sign in, change configuration, enable logging or process messages.

## Edition and evidence boundary

Source: **SAS Message Schema: User’s Guide**, **2026.03**, March 13, 2026, `v_030-P1:frdmsg`, printed pp. 1–61 (physical pp. 7–67). The supplied PDF has 68 physical pages; printed p. 62 is blank. No appendix or glossary occurs in this edition. These are original operational syntheses, not a redistributed schema, screenshot or example program. Core identifiers below are factual reference keys, not a replacement schema definition.

The source's type-mapping table on printed pp. 24–25 has malformed extraction and a visually displaced Date row on p. 24. Where a cell's interpretation is uncertain, require the target release's supported contract; do not manufacture corrected syntax or bounds. Source review is not a serialization, rule-compilation or runtime test. UI icons may be absent from extraction; identify an action by its named resulting dialog, and stop if the installed control cannot be established.

## 1. Describe the structure before choosing types

Sources: pp. 1–4, 19, 37–40, 47–48.

Record each complete field path, parent set, object versus repeated-object structure, scalar versus scalar-array type, cardinality, units, access, missing/default behavior and consuming systems. A variable is metadata for a value, not the value itself. An **Object** set groups one record; **Array of objects** repeats that group. A scalar array repeats a single field type, not a record. Ordinary sets may nest; profile sets may not. The automatically created root shares its schema's name, represents flat fields and is conventionally omitted in diagrams. The illustrated customer and loan hierarchies demonstrate grouping/repetition, not prescribed financial fields.

Path length is at most 4,000 characters with Postgres or 4,000 bytes with Oracle; downstream systems can impose additional limits. SAS-provided ordinary schemas are prescribed templates, not permission to alter the read-only Core schema. There is no documented small fixed count of ordinary variable sets; that does not remove path or downstream constraints.

Use the variable table to check type and array bound, string length, rule-reference count, access and default. The flattened set view shows the message structure compactly. Enable **Display Name** through the column selector when needed; it is hidden by default. A rule-reference count is a dependency signal, not evidence that every referencing rule is deployed or exercised.

## 2. Select types and serialization deliberately

Source: pp. 23–25. First bind the producer encoding (JSON or Ion), rule access and consumer encoding; then use the release's mapping for that combination. In particular, a field's name **Big integer** does not establish lossless integer arithmetic in a rule.

- **Integer** uses DS2/rule `int`, with bounds −2,147,483,648 through 2,147,483,647; JSON is integer and Ion is `int` for input and both output access modes.
- **Big integer**, **Number** and **Currency** use rule `double`. The table prints `4.94065645841E-324` and `1.7976931348623157e+308` as the accepted endpoints; it does not provide a reliable negative-value or exact-integer guarantee. Establish needed precision, signed domain and currency scale against the target contract instead of treating the first value as a complete mathematical signed bound. Currency otherwise follows Number, with possible solution-specific limits.
- For **Big integer**, Ion input/read-only output is integer, but read-write output is float. **Currency** uses Ion decimal input/read-only output and float read-write output. **Number** accepts/emits float or decimal when read-only, but emits float when read-write. All three are JSON number. Plan round-trip checks before changing access or relying on decimal precision.
- **Boolean** maps to rule `int` with 0/1, JSON Boolean and Ion `bool` for input/read-only output; the read-write output cell is printed `Boolean`. Do not silently treat differing source labels as an independently verified wire contract.
- **String** maps to rule `varchar`, JSON/Ion string, with table bounds 0–65,535 characters. Set each field's actual permitted length; the type ceiling is not its configured default.
- **Time** maps to rule `double`, JSON string and Ion timestamp. Its printed numeric bounds are 0 through 86,400. Ion input/read-only output ignores the date; read-write output fixes the date to `1970-01-01`. Define timezone and end-of-day acceptance from the actual contract before testing.
- **Timestamp** maps to rule `double`, JSON string and Ion timestamp. Printed bounds are `-11928470400` (`01jan1582:00:00:00`) through `569318630400` (`01jan20001:00:00:00`). Preserve the source's year **20001** rather than silently correcting it; confirm required range and lexical format with the target interface.
- **Date** has a visually displaced mapping row. It includes `double`, `-138061`, `01jan1582`, `6539336`, `01jan20001`, `string`, and timestamp cells saying the time is ignored. These tokens alone do not establish correctly aligned per-column mappings. Resolve the owning release contract before offering executable conversion, numeric bounds or date wire syntax.
- A scalar **array** supports a supported element type, at most 1,000 items, JSON array and Ion list for all three input/output columns. An **Array** variable set is an array of DS2 packages and is printed as list of struct in the encoding columns. An **Object** variable set has a separate continuation row on p. 25; consult that row and the target contract rather than inferring object encoding from the array row if its cells cannot be read reliably.

Prepare type acceptance cases for integer boundaries, required signed/precision cases, string character versus byte limits, date/time zone/format edges, zero/one/maximum/overmaximum array lengths, and read-only versus read-write round trips. These are proposed checks, not observed results or new product guarantees.

## 3. Complete the field-property contract

Sources: pp. 27–28, 37–44, 49–58.

| Property | Ordinary schema/set/variable | Profile-specific distinction |
| --- | --- | --- |
| Schema identity | Unique name: letters, numbers, underscores, spaces; immutable after creation. Type: lowercase alphanumeric, used for categorization; cannot be `profile`. Description: 999 characters. Tags are static labels, each committed with Enter. | Organization creates its one profile schema, using its name. Do not copy or create an ordinary schema as a substitute. |
| Set identity | Case-insensitive unique name, up to 127 letters/numbers/underscores; description up to 999. Create under a local selected parent in a Developing schema, never within a linked component. | Create at the profile root; same name/description constraints; up to ten string keys from organization-associated ordinary/reusable schemas. |
| Set/cardinality | Object or Array of objects; repeated-object maximum 1–1,000, default 10. | No nesting or component links. Cache expiration defaults to 730 days without signature update, after which the signature is deleted. It is not an aggregation window. |
| Variable identity | Case-insensitive unique name, up to 127 letters/numbers/underscores; unique display name up to 255, initially the variable name; description up to 999. | Name up to 127 with the same permitted characters; unique display name up to 255; description up to **1,000**, not 999, in both creation routes. |
| Access/ownership | Read Only by default; Read Write allows rule mutation. Access type cannot change after Save. | Parent project owns writes. Sharing defaults to The parent project only; All projects in this organization gives other projects read-only access, not writes. Preselecting Project makes Parent Project read-only in the dialog. |
| String length | Explicit length; cannot reduce maximum after deployment. | Profiles creation asks for minimum and maximum length; rule-editor creation describes a length. Do not assume both forms expose identical inputs. Existing profile data length can increase, not decrease. |
| Scalar array | Optional maximum items 1–1,000, default 10; no array default. Cannot decrease maximum after message-schema deployment. | Same creation cardinality. Existing profile array maximum can increase, not decrease. |
| Default | Optional for a non-array variable; table shows value used when unspecified. | Documented in rule-editor creation, not in the separate Profiles creation sequence. Do not infer automatic zero, absence semantics or initialization rules. |
| Value restriction | More → Limit values → Values accepts enumerated String, Number, Integer, Big integer or Currency entries, committed with Enter. Numeric Range uses lower/upper bounds and independently excludes either or both endpoints. | Same supported enumeration/range types and endpoint choices in both creation routes. |
| Required | Missing data for a required incoming field rejects the message. | The profile creation sequences do not document an equivalent Required field. |
| Deprecated | Signals planned non-use/removal or change, not removal itself. | Do not invent an equivalent profile control from the ordinary variable form. |
| Save | Save closes; Save and create another saves and reopens a fresh creation form. Inspect the success message and resulting set/variable. | Same repeated-create option for the Profiles route; rule-editor route documents Save and then `profile` completion suggestions. |

For a schema-field masking request, use **More → Data masking** and specify the intended display behavior. Ordinary strings default to **None**, and document **Mask all**, **Mask beginning** (retain last four), **Mask end** (retain first four), **Mask middle** (replace the middle four), **Mask email domain** (non-space characters in the domain) and **Mask email user** (non-space characters before `@`). Profile creation documents only email-domain, email-user, end and middle methods. The examples illustrate character replacement, not encryption or a guarantee about malformed/short strings. Output depends on the displaying tool; inspect each authorized consuming surface and never claim log/export protection from this metadata alone.

For rule-editor profile creation, start only with an existing rule and organization Profile Editing permission. Use the create-profile-variable action to open **New Profile Variable**, select the existing profile set, fill identity/sharing/type/array/default/masking/limits, then Save. The rule supplies the project context; creation does not implement an update rule. Type `profile` to discover available variables, but do not treat autocomplete as a state-transition test. The tap-purchase example on p. 48 illustrates a rule-maintained count; neither its initial zero nor its referral threshold is a universal profile default.

## 4. Review Core fields by responsibility

Sources: pp. 4–19. Incoming **ION** schemas must include the supplied **Core** schema (p. 29). Core is read-only in the editor. Do not recreate it from these notes, change its standard variables, infer a new field from a label, or use an unavailable output as a rule input. Prefixes below follow the manual's local table identifiers; determine the full path from the actual Core tree (`message.request`, `message.sas.*`) before mapping payloads.

### Request and response control

Source: pp. 9–12. Most Request fields are read-only rule inputs; `logLevel` is marked not applicable in the source table.

- Required strings: `request.messageClassificationName` (maximum 80), `request.schemaName` (maximum 100). Align both to the saved classification/schema, not to an approximate display label.
- Optional read-only inputs: `clientAmount` (Currency, normalized US-dollar amount, default 0), `clientDecision` (Integer, client decision), `command` (String up to 8, default Execute; examples Execute/Validate/Describe), `decisioningInd` (Integer, default 1: models+rules; 2: rules only; 3: models only), `messageDtTm` (Timestamp, customer local event with timezone), and `messageVisibility` (String up to 100, alert-triage visibility input).
- `request.messageIdentifier` is a customer-provided String up to 36, separate from the generated system identifier. The table does not label it required or optional; resolve target requiredness rather than guessing.
- `request.restResponse` is Integer: 0 returns the earlier of SLA timeout or processed response (default); 1 acknowledges then processes; 9 requires a response while ignoring SLA timeout. This is response control, not proof of processing success or permission to retry.
- Deprecated `request.restResponseFlg` (Boolean, 2025.08) used 0 for no response (default), 1 for required response. Do not map its numeric meanings directly onto `restResponse`.
- `request.logLevel` is Integer, default 0. The manual describes value 13 for detailed processing information only when runtime logging is enabled with `SAS_SCR_LOG_LEVEL_App.tk.Detection=INFO`. This is an exact source identifier, not an instruction to enable logging or expose customer messages; obtain explicit logging authority and target deployment evidence first.

### Decision and alert summary

Sources: pp. 5–7. These output fields are marked not applicable for rule access.

- `alerted` is the post-execution alert-recommendation summary array. Its String members are `outcomeEntity` (up to 100), `outcomeEntityType` (up to 15), and deprecated `outcomeEntityInd` (up to 1, 2025.05). A recommendation is not evidence that an alert was persisted or worked.
- `decision` summarizes executed rules/models. `outcome` is Integer: 0 unknown/not applicable, 10 approved, 20 verification, 30 referral/hold, 40 decline/reject, 50 pickup, 60 ignore. String members: `outcomeName` (up to 20), `outcomeEntityType` (up to 15), `outcomePrioritizationCode` (up to 4, used together with outcome), `referenceIdentifier` (up to 20, most restrictive rule reference), and deprecated `outcomeEntityInd` (up to 1, 2025.03). `dndDtTm` and `outcomeUntilDtTm` are Timestamps for do-not-disturb and outcome-validity timing. Do not turn names, priority strings or timestamps into an undocumented precedence algorithm.

### Per-model and per-rule evidence

Sources: pp. 7–8, 12–15.

- `modelfired` repeats execution data per model. Integer fields: `buildVersion` (not rule-accessible), `elapsed` (microseconds, read-only), `score` (read-only) and `supplementalScore[]` (read-only integer array). Strings: `outcomeEntity` (up to 100) and `outcomeEntityType` (up to 15), neither rule-accessible; read-only `referenceIdentifier` (up to 20), `returnDesc` (up to 4), `returnDetails` (up to 100), `returnType` (up to 2), `scoreExplanation` (up to 100) and `supplementalScoreExplanations[]` (each up to 100). Do not confuse this String `returnType` with the Integer system return type, or assume a score is a probability.
- `rulefired` repeats rules meeting both schema and organization eligibility. Every listed member is marked not applicable for rule access. Boolean fields: `alertFlg` (recommendation), `disabledFlg`, `firedFlg` (condition/method firing), `outcomeFiredFlg` (negative outcome condition), `overtimeFlg` and `skippedFlg` (exit-all-rules skip). These flags answer different questions: an eligible/recorded rule is not necessarily fired.
- Its Integer members are `elapsed` (**nanoseconds**, not model microseconds) and `outcome`; `outcomeDtTmUtc` is the execution Timestamp. String members: `alertReason` (length 765), `outcomeEntity` (up to 100), `outcomeEntityType` (up to 15), `outcomeName` (up to 20), `referenceIdentifier` (up to 20), `ruleIdentifier` (up to 36), `state` (up to 15, production/testing), and deprecated `outcomeEntityInd` (up to 1, 2025.08). Keep the two rule identifiers distinct in evidence records.

### System attribution and timing

Sources: pp. 15–19.

- `system.messageDtTmUtc` is the received Timestamp and is read-only rule-accessible. The other System members below are marked not applicable for rule access.
- Strings: `messageClassificationNode` (up to 36, hierarchy key derived from classification name), `messageIdentifier` (up to 36, system-generated), `organizationName` (length 16, deployed-image name), `organizationIdentifier` (length 36, deployed-image identifier), `processInd` (up to 1; blank means decision inside SLA, T means timeout), `returnDesc` (up to 4), `returnDetails` (up to 100), `schemaVersion` (up to 12, version used for this message), and deprecated `transactionIdentifier` (up to 36, 2025.01).
- Integers: `packageVersion` identifies message-preparation configuration; `returnType` has 0 OK, 4 runtime error where retry is possible, and 8 unprocessable message. A possible retry is not a safe automatic replay guarantee; reconcile effects/identity first under the orchestration owner.
- Deprecated `system.transactionDtTmUtc` (Timestamp, 2025.01) described received time. Do not conflate the customer local event timestamp with the system received timestamp or infer semantic equivalence merely from a deprecated label.
- All `timings` members are Integer microseconds, not rule-accessible: `models`, `post`, `prep`, `profileFetch`, `profileUpdate`, `rules`, `total`. They report model execution, response posting, preparation, Redis profile retrieval/update, rule execution and total processing respectively. Do not sum them into an undocumented SLA formula or confuse their microseconds with `rulefired.elapsed` nanoseconds.

The Core tables' String length entries often show `0–N`; they are size metadata, not a new declaration that an otherwise required Request field may be missing. No deprecation above proves that its replacement is present or backward-compatible in the installed release.

## 5. Find, reuse and change the right revision

Sources: pp. 19–22, 27–35, 38–45, 59–61.

1. **Locate with existing visibility.** Use the site's case-sensitive `SASDetectionDefinition` application path and actual URL, not the manual's placeholder host. SSO can omit the sign-in form. Missing `sda.navigation.*` capabilities can hide Detect Behavior. A granted home page shows the most recent 20 viewable items across supported object types; Filter, tile/list view, list column sorting, refresh and Open operate on that view, not the complete catalogue.
2. **Search the catalogue, not wildcards.** The Message Schemas Filter is case-insensitive and does not accept wildcards. Its category selector defaults to all categories. For column filters choose **Filter column**, a type-appropriate comparison, a value and **Apply**; supported fields include Name, Description, Date Modified, Type, State, Created By and Date Created. A missing result does not establish that a schema does not exist outside your access group.
3. **Choose shared versus independent maintenance.** A composite is the whole schema plus zero or more components; a component is another schema linked at a selected local set. Links inherit component changes, and component content is read-only in the parent. Only accessible non-profile schemas appear in **Choose Message Schemas**. Public composites may link only public components; restricted composites may expose restricted component content to their own readers without giving those readers standalone access to that component. Review this disclosure before linking.
4. **Record reuse choices when copying.** Select a non-profile schema, open **Copy Message Schema**, give a unique name/optional description and review each reusable child: Copy creates a separately named reusable schema, Link retains the original shared child, clearing Include omits it. A copied child still has to be edited by opening that child, not through its parent. It can itself later be shared; Copy is not perpetual isolation. Save, then inspect the actual tree and dependencies.
5. **Remove a link, not the child object.** Open the composite, select the association, invoke its remove action and require the association-removed confirmation. Review affected consumers first. Removing an association does not establish deletion of the reusable source or rollback of deployments.
6. **Record observed versions.** In Versions, `(viewing)` identifies the displayed revision. Only the latest may be Developing and editable; Deployed is immutable. New version starts from the latest revision. The documented major category includes breaking deletion of deployed/used objects or relations, creation/copy/import of a schema or set, and deployment; minor covers backward-compatible sets/fields/relations; patch covers compatible attributes. These categories are not a client-side version generator: retain actual product version and change evidence. In-use Developing schemas still prohibit breaking changes. Coding → Testing can cause an organization-linked schema to be checked, revised and used by the updated deployment/organization.
7. **Keep access changes monotonic when in use.** Properties exposes access scope; the membership action opens **Manage Access Group Members**, with user/group filtering and selected versus available lists. Save and inspect the result. At least one identity is required for selected access. Once used by an organization/project, access may expand but may not narrow, including removing a selected member. A restricted component prevents switching its composite to All users. Environment Manager group changes can independently change effective readers; record those dependencies rather than asserting the schema list alone freezes access.
8. **Delete only the approved object.** A schema must be Developing with no message/organization relationships. Set deletion requires Developing state and excludes root/private sets; profile sets must first have their profile variables removed and may not be in use. For variables use the selected set/field, deletion action, confirmation and success result; check rule dependencies rather than following the ordinary deletion subsection's mistaken opening phrase “To add”. Never bypass an in-use restriction by deleting dependent rules without approval.
9. **Constrain profile edits.** Owning-project membership plus organization Profile Editing are required for edit/delete; deployed profile variables cannot be edited. Documented edits are description, sharing, increased string length and increased array maximum. Shared-to-private is forbidden while Testing/Production rules use it, and in-use variables cannot be deleted. Open the owning Profiles → set → Project → variable → **Variable Properties** and Save; retain the resulting revision and dependency outcome. Type, ownership, keys, defaults or persisted-signature migration are not established in-place edit operations by this procedure.

Finish with an offline or observed change record: full paths and type/wire/precision decisions; bounds/enumerations/defaults/requiredness; access and component-disclosure review; project/key/sharing/expiry; dependent rule counts and exact schema revisions; expected success/rejection cases; unknown cells or unsupported operations; and performed versus unperformed verification. Unknown contracts block their dependent live steps, not completion of the prepared specification.
