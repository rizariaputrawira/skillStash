# Fraud reporting and analytical handoff

## Applicability

For building a fraud operations/strategy report, receiving a model for engine/strategy acceptance, or using an available Copilot assistant. Report UI basis: supplied *SAS Visual Analytics: Designing Reports*, **2026.04–2026.05**, printed pp.7–10, 29–32, 46–49; SFD data constraints: *SAS Fraud Decisioning: User’s Guide*, **2026.03**, pp.197–199. These separate product editions do not establish a jointly tested installation. [SOURCES.md](../SOURCES.md) records identities and limitations.

When the report task includes templates/layout/themes, state/recovery, printing/summaries, distribution/sharing/embedding, packages/localization/settings, URL mappings or promotion, read [report operations](report-operations.md). These procedures supplement the fraud metric workflow; their source edition and visual-review limits remain distinct from live UI verification.

## Build a fraud report in Visual Analytics

1. Obtain authorized reporting data already available in CAS, its grain/keys, source revisions, refresh time and allowed audience. Agree metric definitions before selecting a chart: eligible transaction count, distinct alerted transactions, alert count, reviewed messages and confirmed outcomes are different quantities. Preserve currency and outcome-maturity windows. Do not infer a ready-made report dataset from the deck's demo titles.
2. In Visual Analytics, use **New report**. In **Data**, choose **Add data**, select the prepared source in **Choose Data**, then **Add**. Confirm the source is the intended table/snapshot, not an identically named table in another caslib. If data is absent, prepare the loading/access request; selecting a skill does not authorize importing transaction data.
3. Add a table or graph from **Objects** to the canvas, then assign the required data items from **Data**. Use **Options** for object presentation and verify data role assignments and aggregation. Build a detail table alongside the requested aggregate during verification so count inflation and filtering can be reconciled; do not expose protected identifiers to unauthorized viewers.
4. For a strategy-impact page, compare incumbent and candidate on a matched event population, dependency/state basis and label cutoff. For an operations page, show queue/workload age and review/feedback completeness separately from mature fraud outcomes. Define each rate's numerator and denominator; do not average subgroup percentages without weighting their denominators.
5. Add pages as needed using **New Page** in **Outline**. Apply the intended filters and inspect the same cohort in each relevant object. If a live page is required, configure **Periodically reload page data** under page options deliberately; without it, the guide says a page does not automatically update unless a query is initiated. A refreshed chart still depends on source-data freshness.
6. Use **Save** or **Save as** into the authorized folder, then **View report**. Reopen and inspect as the intended viewer where authorized: default filters, page navigation, totals, absent data and access restrictions must still be correct. Sharing or scheduled distribution needs its own audience/data authority. The guide warns that **Save as** does not copy existing report distributions and copies display-rule alert conditions without their recipients; do not assume a copied report preserves delivery.
7. Return report identity/location, source and refresh lineage, metric contracts, filters/aggregation, reconciled keyed counts, viewer checks and unperformed layers. Report only observed values; no benefit, prevented loss or causal improvement follows from a chart alone.

### Synthetic calculation check

Given 1,000 eligible transactions, 100 alerted transactions, 20 reviewed and 8 confirmed fraud with 12 unresolved: alert rate is 10%, review coverage among alerts is 20%, and the currently confirmed share of reviewed cases is 40%. That 40% is neither population recall nor established mature-label precision. Non-alerted and unresolved outcomes are missing. A rule that fires twice on one transaction must not double the distinct-alerted-transaction denominator.

Check field availability before designing historical views: the consulted SFD output-filter feature removes profile data by default and does not retroactively backfill later-added profile fields. Inspect the actual topic/filter/table contracts; a report cannot reconstruct evidence that was never retained.

## Prepare a model for the fraud strategy

This branch is for the SFD engineer receiving producer evidence and checking its use in the actual target, not reproducing model development or granting model/strategy approval. The acceptance recipe below is an independently authored safeguard; supported operations remain bound to the target's release and documentation.

1. **Inventory the supplied packet and gaps.** Record recipient/producer roles, authority, intended SFD release/environment, scoring surface and requested acceptance criteria. Obtain model/artifact and schema identities; feature/label/time definitions; frozen transformation ownership; score/event/scale/error contract; and keyed offline-parity inputs, expected/actual results, artifact identities and declared tolerances. Retain the producer's evidence rather than rerunning fitting, label construction or export. If no packet exists, request these fields from their owners, mark each absent item `not established`, and still finish the proposed target mapping and acceptance plan below with explicit unknowns. No sibling package is required.
2. **Map the producer requirements to the actual SFD target.** For each input, record the supplied definition beside the actual message/profile/signature field, schema/version, entity key/grain, type/shape/units, category mapping, availability/window/cutoff and missing/default/expiry behavior. Record profile initialization and read/update order relative to scoring, including whether the current message is included and how late messages are treated. Check target evidence against the producer's required states; a current profile is not proof of historical availability. Carry label event, maturity/correction policy and evidence cutoff into the interpretation of supplied results, without reconstructing labels. Finish with a mapped/mismatch/not-established row for every required input and an owner for each gap.
3. **Resolve score and transformation ownership.** Map the supplied output/event/class to the actual score consumed by rules; retain scale, direction, units, missing/error behavior and the existing threshold identity, comparison and equality rule. A score on a 0–900 scale is not a probability simply because it can be divided by 900. For each supplied transformation, identify its actual implementation in producer preparation, artifact or SFD consumer and check that it runs exactly once, in the required order. Flag missing or duplicate stages, changed artifacts or unsupported dependencies for the responsible owner; do not invent transformations, refit or select a new threshold to make results agree.
4. **Bind the supported acceptance path.** Check the exact package/language/signature and runtime support against the intended target, not the export filename or offline pass. When model association or supported engine score matching is requested, read [rules, testing and deployment](rules-testing-deployment.md), especially its model branch, before planning or executing those operations. Use its release-specific prerequisites, mapping/shared-effect checks and applicable supplied validation-output path; do not assume MAS equivalence or a universal package format. Missing compatibility evidence blocks activation, not preparation of the acceptance plan.
5. **Prepare keyed target acceptance cases.** Reuse the producer's declared tolerances and expected intermediate features/scores, and bind them to actual target input/state and artifact revisions. Resolve missing tolerances before judging numeric agreement; do not relax them after observing results. Include pre- versus post-message profile state, unavailable-at-decision-time features, empty versus zero, schema/shape/units mismatches, missing keys, unseen categories, extreme-valid and nonfinite inputs, and late/out-of-order messages as applicable. Include below/at/above the supplied threshold with its exact equality behavior and cases exposing omitted/double transformations. For example, a supplied `score >= 400` comparison expects false/true/true at 399/400/401. Specify expected score, rule/final strategy outcome and state/effects separately; unknown behavior remains an unresolved case, not an invented fallback.
6. **Execute only the authorized target checks and reconcile results.** Use the supported local procedure above only within granted test/association/execution authority. Compare actual keyed feature states, scores and consuming rule/final strategy outcomes with expectations; check missing, extra and duplicate results and reconcile counts. Record numeric and decision discrepancies separately: a tolerance pass does not excuse crossing a decision boundary. Capture exact model/transform/association/rule revisions, initial state, runtime/job identities and observed effects. If only offline evidence is available, report that evidence as supplied; mark target scoring, engine acceptance and strategy execution `unperformed` or `not established` with reasons and return the complete proposed cases. An offline decision flag, saved association or loaded artifact does not prove a running strategy's result.
7. **Return the consumer acceptance result to the owners.** Deliver the packet inventory and gap requests; target support evidence; field/state/order/score/transform mapping table; proposed versus exercised cases and tolerances; keyed expected-versus-observed counts/discrepancies; and separate dispositions for package support, mapping completeness, engine score matching and strategy outcomes. Identify whether each result was supplied or observed here, its owner and next permitted action. Route producer-definition/artifact gaps back with the failing case evidence; do not force retraining. Keep model training, registration, engine acceptance and actual model/strategy approvals distinct, record only approvals supplied by their authorized owners, and grant none through this procedure.

## Use Copilot only where actually available

The report-design manual describes Visual Analytics Copilot as administrator-enabled, not enabled by default, with credential setup required before enablement. Do not configure credentials, change licensing or enable it merely to write a report. Where already enabled and authorized, request a bounded draft/report change using approved data, inspect the proposed/generated result, and verify source selection, fields, aggregation, filters and numbers exactly as for manual authoring. Never paste customer data or secrets into an unapproved assistant.

This is evidence for **Visual Analytics** Copilot at the consulted edition, not every SFD Copilot capability. The current official SFD product page separately describes assisted rule authoring, but supplies no release-specific UI contract. The deck's planned concepts are not a how-to for ETL, log analysis, model deployment or rule tuning. Obtain the exact target's documentation before those operations; the Agentic AI Accelerator is a different product surface.
