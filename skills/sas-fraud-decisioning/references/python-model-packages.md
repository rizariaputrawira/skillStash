# Python models and behavioral signatures

Load when implementing, reviewing or packaging a Python model/signature specifically for SAS Detection runtime—not a generic SASPy, SWAT or standalone MLServer application. Source: *SAS Detection: Administrator’s Guide*, 2026.03, March 17, 2026, `v_032-P1:frdag`, printed pp92–118. This is original procedural synthesis. The manual's examples and deployment YAML are not bundled or executed. Source coverage remains partial; concrete signature lifecycle and package facts below are not a complete compatibility guarantee for arbitrary models.

## Bind the runtime and feature contract

Record the installed Detection/Python-runtime image and dependencies, model and signature versions, expected feature paths/types, score event/scale, entity key and allowed effects. The documented request path is Detection → gRPC Python runtime → signature handling → MLServer inference → signature serialization/persistence. In that path the signature is updated **before** inference; do not assume the model receives pre-message history. Generic profile-variable rule order and Python signature lifecycle are separate contracts.

A signature is keyed behavioral history stored in the Profile Store, not an arbitrary Python global or a model file. Choose only required entity histories; the manual's typical five/six signatures is design advice, not a hard supported maximum. Resolve entity key scope, expiry, duplicate/late events and schema evolution from the actual model/runtime contract.

## Implement and package

1. Implement a class inheriting `mlserver.MLModel`, with `load()` and `predict()`. Keep the model name stable and increment its version deliberately. Load trusted artifacts and ancillary data relative to the package directory, not an operator's working directory. The source uses Pickle; loading untrusted Pickle is unsafe. This guide does not authorize deserializing supplied artifacts.
2. Use the runtime's `pythonmodelruntime.utils.decode_and_extract_args` decorator on `predict()` as documented. MLServer inputs are list/array-shaped, while Detection processes one inference and the helper extracts the length-one input into scalar arguments. Declare actual input names/types consistently across code, settings and message mappings. Return the model score as a NumPy array. Do not infer a probability from the source's illustrative score scaling.
3. For a model using signatures, initialize them using the runtime's `init_signatures`/`get_signatures_path` interface and make each required signature an input in both `predict()` and `model-settings.json`. Bind the signature instance by its versioned class name; it is not fetched ad hoc through a general Redis client inside the model.
4. Implement the signature contract: `__init__()` initializes state; `resolve(**kwargs)` returns a string key or `None`; `update(**kwargs)` returns a Boolean persistence decision; `serialize()` returns bytes; `deserialize(bytes)` restores state. An empty/None key prevents fetch. `resolve` and `update` must accept the inputs declared by the signature settings. A successful fetch invokes deserialization; persistence follows `update() == True`. Test new entity, existing entity, unchanged state, absent key and serialization-version incompatibility separately.
5. Keep serialization explicit and round-trip-check all persisted members. Choosing JSON/Struct/Pickle has compatibility, trust and precision consequences; no automatic migration of historic signature bytes is established. Do not change a class layout and assume old bytes will deserialize correctly.
6. Assemble model source, `model-settings.json`, and required model/data files in a model-named directory. Package signatures separately with their class source and `signature-settings.json`. The source also prints singular `signature-setting.json` once; use the target runtime's confirmed convention rather than inventing an alias. `ModelProperties.json` distinguishes `scoreCodeType` values `SDA-PYTHON-Model` and `SDA-PYTHON-Signature`; reconcile metadata, input `jsonPath` mappings, settings and actual class/module names before import.

## Test, then integrate only with authority

The manual describes a containerized functional harness using gRPC, MLServer and FakeRedis. This is an isolated emulation path, not evidence of production Redis behavior or deployment readiness. Use the installed release's delivered harness and trusted images when explicitly authorized; do not reconstruct a Docker invocation, install dependencies or use an unpinned `latest` example from this guide.

Prepare keyed cases with expected signature before/after, model inputs, score and persistence. Compare a no-signature baseline and signature-consuming model only when appropriate. Test length-one input decoding, missing keys/features, serialization round trip, score/event mapping, unseen ancillary lookup keys and repeat/late-event policy. A ping or successful model import does not exercise those transitions.

For deployment, import the supported package into Model Manager's **Detection Repository**, then follow [model association and deployment](rules-testing-deployment.md#3-if-the-rule-uses-a-model-associate-and-prove-the-model-first). The documented Python deployment additionally requires an init container that stages packaged models, a Python-runtime container and shared model volume. Reconcile `SAS_MODELS_PATH`, `SAS_SIGNATURES_PATH`, runtime HTTP/gRPC ports and the same approved profile-store configuration as the Detection container; do not copy example names, plaintext secrets or YAML placeholders into a site.

MLServer `settings.json` controls logging through `logging_settings`; debug/file examples are not production logging policy. Return package/class/settings identities, dependency/runtime compatibility evidence, signature transition and score-parity results, association/deployment/loaded status and all unperformed checks. Unknown image, settings schema or deployment details block those operations, not preparation of the package review.
