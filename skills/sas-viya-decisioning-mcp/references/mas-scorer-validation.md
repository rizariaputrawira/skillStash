# MAS input and batch validation

Load when mapping tabular/file inputs, validating data grids or reviewing batch/regression scoring of an authorized published decision. This is an offline preparation and review procedure until execution is separately authorized. Source identities and license limits are in [SOURCES.md](../SOURCES.md).

1. **Bind the scoring target.** Record the approved product/release, module and step IDs, published revision and dependencies, exact deployed signature, input-source schema and authorized scoring effects. The scorer implementation informs review; the deployed MCP schema and target-supported MAS contract own actual requests. Do not install the scorer or switch to direct REST to bypass a filtered MCP tool. Follow [publication verification](publication-and-verification.md) for runtime identity and effect authorization.
2. **Prepare a mapping in signature order.** For every input record source column, target name/type, missing/invalid policy, precision, units/date semantics and explicit transformations. Preserve string identifiers and leading zeros; absent numeric values are not zero. A populated value that cannot be parsed is a flagged preflight failure, not a silently submitted zero or null. The source scorer's integer truncation and midnight-based date heuristic are implementation choices, not defaults to adopt. Select date handling from the actual field contract and reject lossy conversions without an approved policy.
3. **Validate data-grid representation.** Separate source-cell serialized text, the fully parsed structure and the actual target input representation. Require full parsing plus target-specific shape/schema checks and decoded value comparisons. Balanced brackets, a `valid_datagrid` flag or a JSON-encoded string alone prove neither validity nor the correct representation. Do not guess a universal data-grid schema.
4. **Account for each batch case.** Keep row/case ID, preflight status, execution identity, returned outputs/errors and comparison result. Choose bounded concurrency from actual environment limits; do not inherit the scorer's concurrency range, retries, breaker threshold or timeouts as requirements. Stop-dispatch, client cancellation and server cancellation/completion are distinct events; record which was observed and reconcile dispatched cases.
5. **Resolve execution before comparing business outputs.** Inspect `executionState`: only a confirmed completed execution with the intended identity and comparable outputs can pass. `submitted`, `timedOut`, missing state and lost responses remain unverified; HTTP 201 or a successful MCP envelope alone is insufficient. Keep uncertain side-effecting execution unresolved and reconcile before replay; do not inherit automatic dropped-connection retries. Compare approved expected actions/reason codes and explicit numeric tolerances. Missing or uncompared results never pass.

The official MAS v8 operation requires signature input order and step-input representation version 1. Its media types are `application/vnd.sas.microanalytic.module.step.input+json` and `application/vnd.sas.microanalytic.module.step.output+json`, not guessed `microanalyticScore.step` names. `waitTime=0` returns submission rather than completed output; positive wait can return `timedOut`; omitted wait waits for completion. These source contract facts are not proof of an installed service's version or a grant to execute it.

## Return

Return a sanitized preflight mapping in signature order; row-level validation/comparison results separating rejected, completed-pass, completed-fail and unresolved cases; execution/revision identities; and an unresolved-state/replay decision. Identify supplied fixture evidence versus live observations. Include no raw customer data. If offline, explicitly state that no scoring occurred.
