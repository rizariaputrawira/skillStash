# Dialect and execution boundaries

Load before selecting dialect-specific syntax, preparing SQL through SAS, or assessing execution plans/cost.

## Bind the parser, not the label “SQL”

1. Identify engine/product, actual release, client surface and where each statement is parsed/evaluated. Use authorized supplied environment/metadata evidence; do not connect solely to discover a version without permission.
2. Map every nontrivial feature to matched official documentation: CTEs, windows/frames, date arithmetic/timezones, parameters, casts/division, null behavior, identifier quoting/case, aggregate variants and plan syntax. A client library version is not the server version. A compatibility mode is not proof of complete equivalence.
3. This package supplies a **PostgreSQL 17 documentation-backed example**, not an all-warehouse syntax layer. Other PostgreSQL versions and SQLite, DuckDB or warehouses require their own matched feature checks; no cross-engine runtime compatibility was tested. If support is unknown, label it **unknown** and return a dialect-independent relational plan or block that syntax-dependent portion. Label **unsupported** only with evidence for the actual target.
4. For SAS, distinguish PROC SQL, PROC FedSQL, CAS execution and explicit remote database pass-through. Do not emit generic `WITH`/`OVER` syntax as if PROC SQL accepted it; require matched product/release/execution-context documentation before asserting support or alternatives. Inside explicit pass-through, bind the remote database dialect and version, while separately verifying the SAS wrapper and connection contract. A remote feature does not establish the same local SAS feature. SAS syntax, missing-value semantics and translation belong to matched SAS programming guidance, not this package's PostgreSQL example. Without that evidence, prepare source/output grains, metric formulas, cardinality checks and a logical plan safely; do not guess runnable SAS syntax.

## Plan evidence and authorized execution

- Bind permitted input objects/columns, functions/views, parameters, output rows/bytes, elapsed-time and scan/cost budget before execution. Use existing approved query interfaces; this package does not authorize installation, login, connection, index/statistics changes, materialization, exports or data rewrites. Report a recommended access-path/schema change separately if relevant; do not apply it as “analysis.”
- A statement beginning with `SELECT` is not a safety classification. Inspect CTEs, locking clauses and called functions; PostgreSQL 17 `WITH` can contain modifying statements, and `SELECT` can include locking clauses. Views/functions may require further authorized inspection. Unknown effects block execution until reconciled.
- Even bounded result size does not bound scanned rows or aggregate/sort work. `LIMIT` is not a cost cap. Use the platform's existing approved controls; if no safe bound is available, return the query and missing-budget prerequisite rather than submitting it.
- For PostgreSQL 17, plain `EXPLAIN` supplies a planner estimate; an observed estimate is not measured execution speed. `EXPLAIN ANALYZE` **executes the statement**, discards ordinary query output but not its side effects, and requires execution authority and budget. Planning also consumes resources; do not treat plain `EXPLAIN` as authorization-free. Do not use rollback as permission to run an otherwise unauthorized statement or as proof external effects cannot occur.
- Record actual engine/version, statement/parameter identity, data scope/snapshot, plan mode, estimated rows/cost, and, only if observed, actual rows/loops/timing/buffers. Cost units are not milliseconds or cloud billing units. Compare alternatives on equivalent semantics, population and conditions; distinguish estimate, observation and hypothesis. Do not invent an index scan, pushdown, CTE materialization or performance improvement from query appearance.
- For a budget breach, timeout or lost response, stop new submissions, preserve the existing identity and inspect completion/cancellation through the authorized execution owner. Reconcile any observed side effects before retry; do not automatically retry or change resource settings. Never expose credentials, PII-bearing SQL literals or sensitive plan predicates in shared evidence.

Official PostgreSQL 17 basis: [SELECT/CTEs/locking](https://www.postgresql.org/docs/17/sql-select.html), [EXPLAIN including execution warning](https://www.postgresql.org/docs/17/sql-explain.html). No SAS syntax support claim is made here.
