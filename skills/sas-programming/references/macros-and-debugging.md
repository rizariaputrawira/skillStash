# Macro and log debugging

## Applies-to and owning sources

[SAS 9.4 Macro Language: Reference, Fifth Edition](https://documentation.sas.com/api/docsets/mcrolref/9.4/content/mcrolref.pdf?locale=en), displayed **September 4, 2026**, owns macro processing, scopes, quoting and diagnostics: chapters 2, 5, 7 and 10, CALL SYMPUT and system-option entries. [SAS 9.4 Language Reference: Concepts, Sixth Edition](https://documentation.sas.com/api/docsets/lrcon/9.4/content/lrcon.pdf), displayed **April 5, 2023**, chapters 8–9, owns DATA step error processing and logs. Consulted **2026-10-28**; [source record](../SOURCES.md).

Applicability is the described Base SAS macro/DATA step facility, not every SAS product or server. Target check: bind actual macro processor, generated-code runtime, product/version and logging permissions through [runtime binding](runtime-binding.md). No maintenance-level range or release delta is established here. The evidenced Compute-versus-CAS macro distinction is owned by that runtime reference, not inferred from the SAS 9.4 manual. Unknown compatibility means offline diagnosis, not guessed submission.

## Isolate cause before patching

1. Collect the smallest failing source region, complete relevant log from its submission, expected output contract, actual schema/counts and runtime identity. Keep the first substantive error and preceding context; later errors can cascade. Redact identifying values and sensitive paths without changing the syntax under investigation. Do not request raw production rows or symbol-table dumps.
2. Classify the failure: source-generation/resolution; compilation/syntax; execution/data conversion; library/permission/resource; or logic/result reconciliation. If the client did not submit or the job is not terminal, obtain that execution evidence through its existing owner rather than diagnosing an invented SAS failure.
3. Reduce to plain generated SAS where possible. For a macro, trace parameter values, local/global symbol scope, generated statements and the point at which code executes. Use `%LOCAL` for working variables within a macro when they are not intended outputs; do not silently change a caller's global state. Macro variables are text substitutions, not DATA step variables or parameterized database bindings.
4. Check timing before adding quoting or delayed execution. A DATA step CALL SYMPUT assigns at execution time; an ordinary `&name` in the same step can resolve before that assignment. Establish a real step boundary before using a newly assigned value in later generated text, or choose an appropriate documented runtime interface for the actual requirement. A DATA step IF does not in itself defer the macro processor. Do not repair phase errors by injecting unreviewed CALL EXECUTE/DOSUBL machinery.
5. Diagnose quoting at the layer that interprets the text. SAS string quotes, macro quoting and SQL literal/identifier rules solve different problems. In the cited edition, `%SUPERQ(name)` takes the macro variable **name without `&`** and masks its value against further macro resolution. This is not general input validation, SQL escaping or permission to execute text. For external values, define a narrow allowed identifier/value contract; do not splice arbitrary text into code.
6. If authorized diagnostics are necessary, enable only the relevant facility in a safe synthetic reproduction: MPRINT shows generated SAS statements, MLOGIC traces macro flow, SYMBOLGEN shows resolution. Capture existing option values first and restore them afterward through the established environment procedure. These diagnostics can disclose values or generated code; do not enable them over credentials/PII or assume keyword masking catches all secrets. Prefer supplied safe expansions or offline substitution when execution/logging authority is absent.
7. Make one causal patch and state what it changes. Preserve intended missingness, grain and inclusion rules. Do not silence NOTES, conversion warnings, repeated-key findings or truncation checks as a substitute for repair. For a permission or unavailable-product failure, report that prerequisite rather than inventing an alternate runtime with different effects.

## Reconcile log and results together

1. Preserve terminal status and step boundaries, then inspect ERROR, WARNING **and material NOTE** messages: uninitialized variables; invalid numeric data or implicit conversion; truncation; missing values generated; repeated BY groups; SQL Cartesian products, remerging or GROUP BY transformation; stopped steps and incomplete outputs. The set of messages is target-dependent, not an exhaustive regex success criterion.
2. Determine whether each expected output was created by this submission or is stale/partial. Compare schema, observation/key counts, duplicate multiplicities, missing counts, domain totals and a few preselected safe boundary records to an independent oracle. Return the mismatch even if the SAS log contains no errors. Reuse [data semantics](data-and-sql.md) for the repeated-key oracle and missing/date/type pitfalls.
3. If the error occurred after a write or execution state is uncertain, inspect the output identity and completeness before resubmission. Report partial artifacts and required authorized disposition. Never delete or overwrite unrelated outputs to obtain a clean retry.
4. Return: cause with supporting source/log evidence; minimal patch; target/source binding; diagnostics used and restored; expected/observed checks; residual risk. Without a live run, label the patch and counts **illustrative/reasoned, unexecuted**. Success requires both correct terminal execution and correct results when live execution is part of the assignment.
