# Offline fraud-engine model scoring handoff

## Load condition and evidence boundary

Load when a developed model is being prepared for scoring inside a fraud decisioning engine, especially when message fields and mutable entity profiles supply features or business rules consume its score. This branch produces the engine owner's input packet from the scoring evidence in [development and evaluation](development-evaluation.md); it does not repeat model fitting, partition design or metric selection. An existing model and its evidence can be handed off without retraining.

The supplied enablement deck motivates the boundary: slides 27–37 connect incoming messages, entity profiles and rule-consumed model scores; slides 53–54 outline packaging, lineage and lifecycle testing. Slides 55–56 contain walkthrough titles in the extracted text, not inspectable model-development or model-card instructions. Source identity and limits are in [SOURCES.md](../SOURCES.md). The following procedure and fixtures are independently authored safeguards, not asserted SAS runtime contracts. No universal SAS Fraud Decisioning (FD), SCR or other engine package compatibility follows from the deck. Target-specific product/release evidence is needed for any supported format, export option, field mapping or execution order; do not invent syntax.

The consumer of this procedure is an analyst or engineer producing an offline handoff for a separately authorized engine owner. The producer owns feature/label/time definitions, frozen transformations, score semantics, artifact lineage and offline parity; the engine owner owns actual target mappings, supported package acceptance and engine/strategy results. Use only supplied or authorized artifacts and synthetic/approved examples. Do not connect to an engine, register, upload, publish, deploy, change profiles or rules, or approve production use under this procedure. Missing target evidence permits a complete proposed handoff with explicit gaps, not an assertion of compatibility.

## Ordered handoff procedure

1. **Identify both ends of the contract.** Record the development model and transformation identities, intended engine/product/release, scoring surface and recipient, and the supplied source establishing each target-specific capability. Distinguish an export artifact from an artifact accepted by the target: a filename or successful export does not prove loadability. Record documented target requirements and separately supplied engine observations with their source, owner, environment and artifact identities; unprovided evidence is not established. Finish with the producer's proposed compatibility table and questions for the engine owner, not an engine acceptance decision.
2. **Reconcile message and profile features at prediction time.** Extend the existing feature ledger with the proposed model-input-to-message/profile mapping for the recipient to verify against the actual target. For each field record entity key and grain, schema/version, type/length/shape, units, category encoding, definition/version, source availability time, aggregation window and cutoff, required profile update timing relative to scoring, and empty/default/expiry behavior. Distinguish a profile before the current message from one incorporating that message; neither order is assumed. State required treatment of late or out-of-order messages and unavailable historical profile snapshots. Compare the training feature reconstruction with the intended scoring-time values, including whether a default differs from unknown. Finish with each field's producer requirement, supporting evidence and known mismatch or unresolved target mapping. A current profile cannot stand in for an unobserved historical profile without qualifying the evaluation.
3. **Make fraud labels time-safe.** Carry forward the existing label ledger rather than redesigning modeling. Record the fraud event definition, observation and prediction times, outcome window, confirmation/availability time, maturity cutoff, reversals or corrections, and unresolved/censored outcomes. Check that a label available only after investigation did not enter a feature or a training population before its availability cutoff. Distinguish a rule-triggered alert, an operational action and a confirmed outcome; none is automatically another's ground truth. Finish with the label-version identity, eligible/excluded counts when available, and any point-in-time reconstruction gap that limits the handoff claim.
4. **Define what the score means before mapping it.** Record output name and event/class mapping, raw versus formatted labels where applicable, score type (probability, rank, anomaly measure or other documented scale), units/range, direction, calibration evidence if a probability claim is made, and missing/error behavior. Record the consuming rule's comparison, equality behavior and threshold/threshold version as supplied, without selecting a new threshold during parity review. Do not infer a probability from the word risk or a bounded number, or infer a universal range/direction from a deck example. Finish with an unambiguous score-to-consumer contract; an unknown scale or event mapping blocks interpreting a threshold.
5. **Trace transformations through export and packaging.** Inventory preprocessing, imputation, encoding, category/reference mapping, scaling, feature order, model computation and output conversion, with the artifact implementing each stage. Assign each transformation exactly once to the producer, export artifact or consumer; identify omissions and double application. For code trimming, export conversion or package changes, retain before/after artifact identities and the changed-stage list, then compare against the frozen development path. Record schema identity/version, model/training snapshot and label references, transformation identities, exporter/tool/product versions when known, export settings, artifact names and cryptographic digests, dependencies and provenance. Use unknown for unavailable facts. Finish with a traceable manifest and a proposed compatible/not-established disposition, not a guessed model-package format.
6. **Specify and, only if separately authorized, execute keyed offline parity cases.** Use the synthetic cases below plus appropriate approved examples. Record expected feature states, expected score/decision behavior, case keys, development and exported/restored artifact identities, numerical tolerances and exact schema/class/comparison expectations before examining results. Compare reconstructed input features as well as outputs; matching final scores alone can hide compensating errors. Compare by keys, check missing/extra/duplicate outputs and count reconciliation, and investigate any numeric difference that changes the supplied consumer comparison. If no offline scorer is available or execution is unauthorized, return expected cases and mark actual values unperformed; never manufacture a parity pass. A decision flag computed offline from the supplied comparison is not an observed engine/strategy decision. An offline scorer's pass does not establish a live engine's ordering or loadability.
7. **Deliver the producer packet and receive questions.** Return the packet below with each mismatch, evidence gap, responsible owner and next permitted action. Separate source-checked design, executed offline parity, supplied engine evidence and production authorization. If the engine owner returns a mapping or result mismatch, retain its keyed evidence and identify the affected producer definition/artifact; do not refit, change thresholds or take over engine acceptance. A handoff can be complete as a documented blocked assessment; missing material evidence cannot become ready by omission. No result in this branch grants engine acceptance or production approval.

## Original synthetic boundary cases

These are contract probes, not observed product behavior. Substitute the supplied contract's actual names and semantics; do not treat the example values as SAS defaults.

|Case|Synthetic setup|Expected checkable disposition|
|---|---|---|
|Current-message inclusion|Previous profile count is 4; this message would make it 5; model contract requires pre-message count|Model input must be 4. Input 5 is a timing mismatch even if both scores are numerically close. Unknown update order leaves compatibility not established.|
|Point-in-time availability|Decision at time 20; profile aggregate becomes available at time 23 although its underlying event occurred at time 18|Do not use that aggregate as available at time 20. A reconstruction using it fails the stated feature contract.|
|Empty versus zero|New entity has no profile value; another entity has a measured count of 0|Keep these states distinct until the frozen missing/default transformation explicitly maps them. Report a mismatch if export or consumption silently substitutes a different policy.|
|Schema and shape boundary|Model expects an ordered three-element numeric feature vector in declared units; candidate provides two elements or changes units|Flag schema incompatibility before comparing scores. Matching column names alone cannot pass.|
|Label maturity|Observation at day 10; confirmation available at day 25; fitting cutoff day 20|Label is unavailable for that fit. Exclude/defer under the established maturity policy, not reinterpret it as a confirmed non-event.|
|Score interpretation|Documented synthetic risk scale is 0–900, higher means more risk; example score is 630|Do not report 0.70 or a 70% fraud probability without an explicit, evidenced transformation and calibration contract.|
|Decision boundary|Synthetic consumer uses score >= 400; cases score 399, 400 and 401|Expected decision flags are false, true and true. Small score differences that cross the boundary need a separate decision-parity failure even when numerical tolerance passes.|
|Transformation ownership|Frozen centering subtracts 10; raw input is 12; exported artifact already centers|Expected model-stage input is 2. Consumer centering again gives -8 and fails transformation parity.|
|Unseen/invalid input|Unseen category, missing required key, extreme-but-valid numeric value and nonfinite numeric value, each with its own key|Compare each against the frozen contract's encoding, rejection or missing-score behavior; do not invent a fallback or silently drop failed cases from the denominator.|
|Late profile update|Two keyed messages arrive opposite their event-time order|Compare each reconstructed window and score against the explicitly declared late-message policy. If that policy is unavailable, return an unresolved case, not an assumed engine ordering.|

## Required handoff result

Return concrete fields, using `not established` or `unperformed` with a reason instead of omitting unavailable evidence:

- **Scope:** handoff ID, analyst/recipient roles, objective, authority limits, intended scoring population and scoring instant, requested versus actually exercised operations.
- **Target evidence:** intended product/release and scoring surface; documentation/source locator and edition; proposed compatibility and unresolved requirements; any supplied format/loadability or engine-test evidence with owner, environment and artifact identity, clearly attributed rather than claimed as producer acceptance.
- **Feature contract:** model-input field, proposed message/profile source, entity key/grain, schema/version/type/shape/units, definition and aggregation window, event/availability cutoffs, required update order, missing/default/expiry policy, training-versus-intended-scoring disposition and evidence; target mapping questions for the recipient.
- **Label contract:** event mapping, outcome window, availability/maturity rule, corrections policy, source/version identity, eligible/excluded counts or unavailable-count reason, leakage and reconstruction findings.
- **Score contract:** output name, event/class, scale/range/units/direction, probability/calibration status, missing/error policy, threshold identity and exact comparison/equality rule, consumer mapping.
- **Artifact manifest:** model and transform identities/digests, schema and training/label snapshot references, export/package identities/digests, exporter/version/settings, transformation ownership and changes, dependencies and unknowns. Store references rather than restricted data or credentials.
- **Parity evidence:** keyed fixture inputs and expected intermediate features/outputs, compared artifact identities, tolerances and decision expectations, actual outputs or unperformed status, matched/missing/duplicate/failed counts, numeric and decision discrepancies, execution environment/log references if exercised.
- **Disposition:** separate statuses for source review, producer feature/label evidence, artifact/transform completeness and offline parity. Attribute any supplied target loadability/acceptance or approval status to its actual owner and evidence; otherwise mark it not established. List blockers, owner and next permitted action; state **engine acceptance and production approval not granted by this handoff**.
