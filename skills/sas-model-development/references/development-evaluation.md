# Development and evaluation

## Execute the development design

1. **Define the estimand and sample.** Write the observation key, population eligibility, scoring instant, feature availability cutoff and (where relevant) label window/maturity rule. Keep target, IDs, partition flags and post-outcome fields out of the feature list unless a justified model specification explicitly uses an appropriate field. Confirm joins preserve the intended grain. Entity IDs can be permitted predictive features in some tasks, but require an explicit generalization and availability rationale, not accidental inclusion.
2. **Choose a generalization test.** For new-entity performance keep related entities in one partition. For future performance use forward cutoffs and only training labels available at each fit time; add an embargo/gap when overlapping observation/label windows would leak. Repeated entities can legitimately span temporal partitions for known-entity future prediction: document that claim rather than falsely calling it new-entity evaluation. Random stratification is appropriate only when independence and sampling assumptions support it. Report label/event counts and whether each metric is estimable; tiny or one-class holdouts do not justify silently reallocating test cases.
3. **Freeze membership before learning.** Save row key → partition/fold with generation parameters and source snapshot identity. Check duplicates, forbidden entity overlap, cutoff violations and unused/missing partition values. If supplied partitions conflict with the evaluation claim, stop fitting, report the conflict and propose a corrected design; do not silently relabel. Do not select a random seed for attractive test performance.
4. **Fit a transformation recipe.** For each learned operation record fit population, learned artifact, missing/unseen-level behavior, feature order and application order. Cross-validation learns preprocessing/target encoding/feature selection within each training fold, not once on all development rows. Prevent self-label leakage in target encoding with a justified out-of-fold scheme. Resampling or class balancing changes the training sample only; validation/test retain the intended assessment distribution or explicit assessment weights. Check how weighting/priors affect calibrated probabilities.
5. **Budget baseline and candidates.** Baselines include training prevalence/constant probability for classification, training mean for squared-error regression or median for absolute-error regression. For unsupervised work compare against an appropriately simple representation/segmentation or explicit operational reference. Declare candidate families, finite trial count, seeds, maximum resources, early stopping evidence and tie-breaking before inspecting final test. Record failed trials, nonconvergence, separation/singularity, dropped rows, missing predictions and changes; no success claim from a submission acknowledgment.
6. **Choose on development evidence.** Define metric denominator, weights, event polarity and direction. Binary ranking can use ROC AUC and precision–recall evidence with prevalence stated; probability estimation needs log loss/Brier score and calibration; capacity-limited decisions need precision/recall or lift at the actual capacity plus costs. Multiclass assessment needs the class set, probability columns and averaging/weighting definition. Regression reports MAE/RMSE in target units, residual bias and relevant tails/segments; percentage errors require a policy for zero/near-zero targets. Neither R-squared nor a p-value alone establishes useful prediction. Set any decision threshold on development data using stated costs/capacity; 0.5 is not a universal optimum.
7. **Evaluate the locked artifact.** If authorized, fit the selected final development model using only the prespecified allowed population; if this includes validation, refit its transformations on that same population and record the new artifact. Apply it to final test without parameter or threshold changes. Report baseline and model on the same eligible cases, confidence/uncertainty method with dependence respected, sample/event counts, segment/time results and exclusions. A poor result is evidence, not permission to retune on test.
8. **For target-free models**, replace supervised event/loss requirements with explicit geometry/scale, stability across permitted resamples, cluster size/profile or anomaly-review utility, reconstruction criteria where appropriate, and domain validation. A silhouette score alone is not business utility. Fit scaling/dimension reduction only on the permitted fit population; verify new-case transformation/assignment support before promising scoring. If labels later guide model selection, disclose that supervision and reserve independent evaluation. Time-series forecasting requires horizon-aware rolling/forward evaluation and model-specific source/technical evidence beyond this package's classification/regression examples.

## Scoring acceptance packet

Specify required raw features and versions, types/lengths/formats, category/reference/event mapping, units, time windows, transformations and their artifact identities. Include missing, unseen-category, ordinary, extreme-but-valid and near-threshold cases. Compare keyed rows, never assumed output order. Explain dropped/multiple rows and missing predictions before metric computation. Declare absolute/relative numerical tolerances and exact class/threshold expectations; investigate tolerable numeric differences that still flip decisions. Preserve logs, output schema, model identity and transformation identity without credentials or PII. This is evidence for the exercised scoring contract, not deployment authorization.
